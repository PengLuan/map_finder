## 一、玩法机制类

### IP-001 随机事件（大雾/夜间/沙尘暴）
- **来源**：专题模式 §2.2 B6（2026-08-22）
- **描述**：巡航模式有概率触发"大雾""夜间""沙尘暴"等临时视野缩减事件，持续 10-30 秒后自动恢复
- **价值**：增加变数与复玩性，考验应变能力
- **暂不做的理由**：增加实现复杂度，且随机性可能影响专题总用时的公平性，与排行榜的"纯竞速"定位冲突
- **复活条件**：若后续加入"娱乐模式"（不计入排行榜的休闲玩法）可考虑

### IP-002 路过地标点亮系统（系统性方案）
- **来源**：专题模式 §2.2 B7 讨论（2026-08-22）
- **定位**：系统性方案，非单一功能点，涉及地标数据、视野判定、视觉呈现、已打卡回溯、个人足迹地图等多个子系统，建议作为专题模式上线后的独立迭代专题
- **核心目标**：让玩家在飞行/巡航过程中，地图视野扫过的地标（预设+已打卡）自动点亮并展示简介，强化"地理探索感"与"足迹回溯感"

#### 系统组成

1. **地标数据层**
   - 预设路过地标：复用 `pois` 表或新建 `landmarks` 轻量表（id/name/lat/lng/icon/category/description）
   - 已打卡地标：查 `player_sessions` 中该用户/session 历史命中的 POI
   - 两类地标在地图上分层渲染

2. **视野判定层**
   - 触发条件：地标中心点进入当前视野矩形（`map.getBounds().contains(latlng)`）
   - 仅判定视野内地标（Leaflet bbox 过滤），百级地标量级无性能压力
   - 触发时机：飞行动画过程中 + 巡航移动过程中 + 手动平移过程中

3. **视觉呈现层**
   - 预设地标：灰色→彩色点亮动画 + 弹出 1 行简介卡片（如"黄河 · 中华母亲河"）
   - 已打卡地标：金色勾选标记 + 可选"上次到访时间"角标
   - 点选模式和巡航模式均启用
   - 可选音效"叮"

4. **去重与状态层**
   - 同一地标本局内只弹一次卡片，已点亮的不再重复弹
   - 已打卡地标点亮后永久保持（本局内）
   - 预设地标点亮后本局内保持彩色

5. **与专题点位的区分**
   - 地标用小图标（如小圆点+图标），专题目标点用大头针，避免混淆

6. **数据沉淀与扩展价值**
   - 为"个人足迹地图"（主方案 D5）积累数据：玩家飞过哪些地标都可在个人页点亮
   - 为"地理百科图鉴"功能铺路：点亮过的地标自动加入玩家图鉴

#### 暂不做的理由
- 涉及多个子系统（数据/判定/视觉/去重/扩展），实现成本高
- 依赖用户历史数据，MVP 阶段用户打卡数据为空，已打卡回溯效果不明显
- 视野判定逻辑需与现有飞行/巡航逻辑深度集成，需充分测试避免性能问题

#### 复活条件
- 专题模式上线运营 1-2 个月，积累足够用户打卡数据
- 确认"个人足迹地图"（D5）进入排期，可与之联动开发
- 作为独立迭代专题立项，而非塞进 MVP

### IP-003 道具系统（跳过卡/提示卡）
- **来源**：专题模式 §2.2 E4（原 E4，2026-08-22）
- **描述**：引入两类道具降低专题门槛
  - **跳过卡**：跳过当前点直接算失败但专题继续（不中断收集链）
  - **提示卡**：免费获得一次方位提示，不消耗积分
- **价值**：降低新手门槛、为变现铺路
- **实现要点**：
  - 道具表设计：`user_items(user_id, item_type, quantity)`
  - 使用记录：在 `collection_progress` 标记该点是否使用过道具
  - 获取途径：登录奖励 / 积分兑换 / 付费购买 / 专题完成奖励
  - 排行榜公平性：使用道具的记录是否计入排行榜需单独讨论（建议单独排行或标记"使用道具"）
- **暂不做的理由**：
  - MVP 阶段先跑通核心玩法，道具系统是"锦上添花"非"雪中送炭"
  - 涉及道具获取/消耗/排行榜公平性多维度设计，需独立讨论
  - 与变现策略强绑定，需先确定商业化方向再设计
- **复活条件**：
  - 专题模式上线运营稳定，确认用户留存数据后
  - 商业化方向明确（免费道具 vs 付费道具的边界）
  - 作为独立迭代专题立项

### IP-004 好友对比（社交功能）
- **来源**：专题模式 §2.2 E5（原 E5，2026-08-22）
- **描述**：结算页显示好友中已完成此专题的人的用时，形成社交比较
- **价值**：社交驱动、增加复玩动力
- **暂不做的理由**：
  - 本期不做社交功能，需先有好友系统（关注/互关关系表）才能对比
  - 社交模块涉及好友关系、隐私设置、动态流等多个子系统，工作量大
  - 当前阶段聚焦单人/PK 核心玩法，社交延后
- **复活条件**：
  - 确认要做社交模块，好友关系系统进入排期
  - 作为社交模块的子功能一起设计，而非单独实现

### IP-005 限时活动专题
- **来源**：专题模式 §2.2 E3（2026-08-22）
- **描述**：节日专题（春节专题、五一专题、国庆专题等）限时上线，过期下架
- **价值**：活跃度、节日氛围、运营抓手
- **暂不做的理由**：
  - 需要运营团队持续产出节日专题内容（选点、文化背景、封面图）
  - 涉及限时上下架机制、专题时效性管理、历史专题归档
  - MVP 阶段先跑通常驻专题，运营机制后续再建
- **复活条件**：
  - 100 个常驻专题上线稳定，基础玩法验证成功
  - 运营团队就位，能持续产出节日专题内容
  - 建立限时专题管理后台（上下架、定时发布）

### IP-006 专题连段（大专题）
- **来源**：专题模式 §2.2 E4（原 E5，2026-08-22）
- **描述**：某些专题可串联成"大专题"（如五岳 + 四大佛教名山 = 名山朝圣大专题），集齐发钻勋章
- **价值**：终极目标、延长生命周期
- **暂不做的理由**：
  - 依赖足够多的常驻专题先上线（至少 50+ 个才有连段意义）
  - 大专题的勋章层级设计复杂（普通勋章 vs 大专题钻勋章的归属关系）
  - MVP 阶段聚焦单专题体验，连段是后期增值玩法
- **复活条件**：
  - 100 个常驻专题全部上线，玩家平均完成 30+ 个
  - 确认大专题的勋章层级与现有铜银金钻体系的关系
  - 作为"集齐成就"系统的子功能立项

### IP-007 PK 干扰道具（雾弹）
- **来源**：专题模式 §2.2 F3（2026-08-22）
- **描述**：PK 专题时可花费积分发"雾弹"干扰对手视野 5 秒
- **价值**：增加 PK 变数、变现接口
- **暂不做的理由**：
  - 需先跑通 PK 专题核心玩法（同步起跑、进度可见）
  - 干扰道具涉及实时同步、反作弊、平衡性调优，复杂度高
  - 可能影响公平竞技体验，需充分测试
- **复活条件**：PK 专题稳定运营后，确认要增加竞技变数时

### IP-008 PK 协作模式
- **来源**：专题模式 §2.2 F4（2026-08-22）
- **描述**：两人分别收集不同点，共同完成一个专题（如 8 点专题一人收 4 点）
- **价值**：新玩法、社交协作
- **暂不做的理由**：
  - 与现有 PK 竞技模式逻辑差异大，需独立设计
  - 涉及分工策略、进度同步、胜负判定等多重新机制
  - MVP 阶段聚焦竞技 PK，协作模式延后
- **复活条件**：社交模块进入排期，或用户反馈强烈需要协作玩法时

### IP-009 断点续传
- **来源**：专题模式 §9.1 问题 1（2026-08-22）
- **描述**：专题中途退出，下次重玩该专题时从上次断点继续，而非从头开始
- **价值**：降低挫败感、尊重玩家时间投入
- **实现要点**：
  - 新建 `collection_progress` 表（user_id/session_id, collection_id, completed_poi_ids, current_index）
  - 退出时保存当前进度，重玩时读取并恢复
  - 防刷分：断点续传的记录是否计入排行榜需单独讨论（建议标记"续传"或单独排行）
- **暂不做的理由**：
  - 本期聚焦核心玩法，断点续传增加状态管理复杂度
  - 防刷分机制需独立设计
  - 简单的"从头开始"规则更清晰，玩家预期明确
- **复活条件**：
  - 用户反馈中途退出挫败感强
  - 防刷分机制设计完成
  - 作为独立迭代专题立项

### IP-010 单点超时机制
- **来源**：专题模式 §9.1 问题 2（2026-08-22）
- **描述**：专题内单点设置超时时间，超时算该点失败（专题继续 or 直接判专题失败待定）
- **价值**：增加节奏紧迫感、防止挂机
- **实现要点**：
  - 单点超时时间按专题星级动态调整（★1 宽松、★8 紧迫）
  - 超时后的处理：算失败但专题继续 vs 直接判专题失败（需讨论）
  - 超时记录标记在 `player_sessions` 中
- **暂不做的理由**：
  - 本期先跑通核心收集流程，不引入时间压力
  - 超时阈值需根据实际玩家数据调优，过早设置可能误伤
  - 超时判定逻辑需与现有单局超时机制整合
- **复活条件**：
  - 收集足够玩家平均用时数据，能合理设定超时阈值
  - 确认超时后的处理策略（失败继续 vs 专题失败）
  - 作为难度调节的辅助手段

### IP-012 几何图形专题设计要点
- **来源**：专题模式原 §八（2026-08-22）
- **描述**：部分专题点位连起来可构成几何图形（五角星、六边形、八角星、爱心、中国版图等），专题结算页额外渲染图形
- **实现要点**：
  - `collections.geometry` 字段标记图形类型
  - 专题结算页把 5/8 个点按收集顺序连成线呈现图形
  - 专题封面图也是该图形的艺术化版本
  - 爱心专题 8 点用最小二乘法拟合爱心曲线 `x=16sin³t, y=13cost-5cos2t-2cos3t-cos4t`
- **暂不做的理由**：
  - 第一期只做基础框架 + 3-5 个专题试运行，先验证核心流程
  - 几何图形专题需要实际在地图上拟合验证点位，设计成本高
  - 等具体设计专题时再考虑（届时移回主方案或 collection-list.md）
- **复活条件**：
  - 第一期试运行通过，准备补齐 100 个专题时
  - 具体设计某几何专题（如爱心中国、五角星）时从点子池取出细化

### IP-013 A2 起点与点位顺序的其他可能性
- **来源**：专题模式 §2.2-A2（2026-08-22）
- **描述**：本期采用"默认起点 + 固定顺序"，以下可能性暂不实现：
  - 从上次离开位置续玩（需断点续传支持，依赖 IP-009）
  - 自选点位顺序（仅非几何专题可用，第一个选的点即起点）
- **暂不做的理由**：固定顺序更简单，且利于几何图形呈现
- **复活条件**：断点续传落地后，续玩自然可行；自选顺序需额外 UI
